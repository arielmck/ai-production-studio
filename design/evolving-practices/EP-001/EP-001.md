# EP-001 — AI Agent Capability, Routing, and Collaboration

Status: Proposed Evolving Practice

Current Standing Rules: none.

## Core Question

How should the Production Studio use and combine AI agents to produce
increasingly robust, maintainable code increasingly quickly?

## Goal

Use each agent where it is currently strongest, in the combination, sequence,
and constraints that currently work best, so the Studio produces code that
works reliably, addresses fundamental causes rather than accumulating patches,
remains easy to maintain and refactor, avoids fragile complexity, and creates
fewer defects and less rework while becoming faster and faster to produce within
each project. As agent capabilities evolve, the resulting lessons should also
improve how later projects are produced.

## Evolving Context

AI agents, coding tools, and the surrounding software-development industry are
changing rapidly. The relative strengths, weaknesses, best sequencing, and
useful constraints of individual agents are therefore temporary conclusions
rather than permanent truths. This Evolving Practice continuously incorporates
new evidence and revises its current synthesis and Current Standing Rules when
capabilities or better combinations change.

## Evidence

The synthesis below summarizes what accumulated pilot evidence currently
suggests, including the Agent Capability Evidence Ledger, which is not kept in a
Studio repository. Individual dated ratings and case narratives stay with that
evidence rather than in this EP.

An additional D-095 investigation on 2026-10-19 exposed a hidden dependency:
Codex Continuation and Agent Handoff used a thread-ID-bearing visible title to
confirm which conversation opened. Introducing descriptive project-and-role
names therefore required revisiting that opening proof across related workflows.
This case illustrates how initially working code can make an ordinary later
change expensive when presentation and operational identity are coupled. It
does not establish a general rate of preventable rework.

## Current Routing — Quick Guide

**As of 2026-10-21; provisional, based on observed performances.** Before selecting agents, identify the task's **one to three most important capabilities**, then choose the smallest combination and sequence that delivers them. **ChatGPT is a participant**: it independently generates architectural alternatives, reconciles evidence, makes value/cost recommendations, and protects user approval boundaries. This guide does not override required consequential-work investigations/reviews, agent access limitations, or explicit authorization. Do not invoke additional agents automatically for simple deterministic work.

| Problem signature / 1–3 key capabilities | Current candidate combination and sequence | Confidence / evidence |
| --- | --- | --- |
| **Runtime failure** — root-cause forensics; process/timing evidence; failure-state analysis | Claude investigates actual logs/runtime; independently task Codex for source and causal alternatives where material; ChatGPT proposes its own alternatives and reconciles; complete required solution review; Claude implements after approval. | Repeated favorable, through Oct 21; October cold-start case confirms complementary strengths. |
| **Uncertain architecture or new consequential feature** — requirements; fundamental alternatives; reuse discovery | ChatGPT settles user outcomes/constraints; independent Claude and Codex investigations; ChatGPT independently invents and compares solutions; Codex reviews the complete proposed architecture before authorized Claude implementation. | Repeated architecture/contract evidence; mandated consequential cycle remains controlling. |
| **Broad simplification review of working software** — elimination of responsibilities; reuse; maintenance economics | Codex and Claude investigate independently with complementary source/reuse lenses; ChatGPT also generates alternative architectures and selects only worthwhile proposals for user decision. No implementation implied. | Provisional proposed routing; this full task sequence is not yet comparatively proven. |
| **Refactoring with behavior preservation** — invariant discovery; structure/reuse; integrated proof | Claude inventories actual coupling and proof owners; Codex challenges structural alternatives and failure contracts; ChatGPT checks whether refactor earns cost and preserves intended behavior; authorized implementer verifies. | Provisional extrapolation; not evidence of a universally best sequence. |
| **Tests pass yet behavior seems wrong** — falsification; state-space; proof adequacy | Codex independently challenges regression oracles and omitted failures; Claude verifies runtime consequences where needed; ChatGPT reconciles what evidence really establishes. | Repeated favorable Codex falsification and Claude runtime evidence. |
| **Provider/host/identity limitations** — native capabilities; exact identities; reuse | Independent Codex technical investigation for supported mechanisms and counterexamples, Claude when live/provider runtime facts are essential; ChatGPT selects human-versus-machine boundary. | Multiple related cases; versions and provider behavior may change quickly. |
| **Small deterministic correction** — implementation; narrow verification | ChatGPT judges value, settled boundaries and current owner; one suitable Implementing agent (currently often Claude) performs the bounded change and proof. | Repeated positive cases; avoid extra routine agent rounds. |

**Two distinct architectural questions must be answered at the appropriate existing stages:**

1. **How could this implementation be simpler?** Reduce state, code, checks and duplication while preserving the proposed design.
2. **What is a fundamentally simpler way to achieve the same result?** Change the sequence, owner, assumption or shared capability so whole coordination, waiting, recovery or other mechanisms disappear.

The first question does not substitute for the second. In consequential work, the initial investigations and ChatGPT's independent synthesis explore both; Codex's complete-solution review challenges both **before** implementation, not concurrently with it. Discovering a smaller patch is not evidence of a simpler system; compare robustness, conceptual complexity, hidden dependencies, preservation, performance and maintenance.

## Evidence freshness and retrieval

EP-001 owns the **current routing interpretation**, not case-by-case scores. The non-repository **Agent Capability Evidence Ledger** retains case ratings (1/5–5/5), date, exact model/version where known, technical topic, independent versus prompted discovery, proven versus proposed outcome, misses, and routing consequence. Ratings describe *specific performances*; do not average across unrelated capabilities. Prefer recent comparable evidence, especially after model/tool changes, but do not automatically discard older verified findings or pretend an untested release shares an earlier score. Maintain one short dated current guide here and append detailed observations to the ledger. When history becomes unwieldy, organize older ledger evidence into dated archives with a simple index without making EP-001 an evidence archive. Update routing on meaningful new evidence, not on a clock or speculative model ranking.

## Current Provisional Synthesis

As of 2026-10-21. These are current evidence-backed observations, provisional
rather than permanent agent rankings.

- Claude currently appears especially useful as the first substantial
  repository investigator/implementer. Observed strengths include strong initial
  comprehension, detailed forensic reconstruction, coordinated implementation
  across existing owners, and generally easy continuation from analysis into
  implementation.
- Claude has repeatedly shown a tendency to begin designing a new mechanism
  before fully discovering existing owners, analogous solved cases, reusable
  code, or reusable concepts. A technically sound initial proposal may therefore
  still be larger than necessary.
- Codex currently appears especially useful as an independent challenger,
  particularly for reuse discovery, ownership and architecture challenge,
  provider/application semantics, counterexamples, state/failure-contract
  analysis, abstraction-boundary problems, and finding cheaper existing
  implementation shapes.
- Codex is not inherently the minimal-solution agent. It can also overengineer
  through retries, recovery, validation layers, fallback machinery, generalized
  robustness, or excessive proof.
- Claude and Codex both tend, once they identify a real failure, to move toward
  engineering protection around the failure. Both therefore need an explicit
  challenge asking whether the fundamental defect itself can first be corrected
  or prevented.
- Recovery, retry, salvage, patching, fallback, and generalized defensive
  machinery should not become the default merely because they are technically
  robust.
- ChatGPT currently adds distinct value by comparing the agents rather than
  being confined to one agent's framing; challenging whether proposed machinery
  should exist at all; identifying user agreements, human prerequisites,
  refusals, deliberate non-automation, and simpler supported boundaries; and
  protecting the distinction between correcting the root defect and recovering
  afterward.
- ChatGPT also has a recurring weakness: a detailed and persuasive Claude or
  Codex analysis can cause it to accept the diagnosis and proposed remedy
  together as one package without independently challenging necessity, reuse,
  root cause, or the human/machine boundary strongly enough.
- ChatGPT has also sometimes carried an agent's solution framing forward too
  quickly instead of reopening the cheaper question: what is the smallest
  worthwhile result?
- On 2026-10-21, Claude's runtime diagnosis identified a slow-start timeout; Codex found a late-terminal/readiness bypass and later proposed reusing the existing readiness helper *synchronously* instead of retaining asynchronous coordination. This deeper simplification was prompted by a user challenge after an incomplete implementation had already been committed; the final architecture's production outcome and performance are not yet verified. ChatGPT did not independently propose it early enough and permitted solution review to overlap implementation. These are distinct capabilities and misses, not evidence for global scores.
- These conclusions describe current observed behavior. New versions, new
  agents, new tools, and new evidence may change them quickly.

## Current Provisional Working Model

A working decision model, not yet permanent policy or a Current Standing Rule.

1. For substantial repository work, Claude is currently often a productive
   first agent because of its combination of initial comprehension, detailed
   investigation, communication, and integrated implementation ability.

2. Use Codex independently when architecture, reuse discovery,
   provider/application semantics, state/failure behavior, abstraction
   boundaries, or a proposed new helper/file/state mechanism could materially
   benefit from challenge.

3. Codex's role is not merely to confirm Claude. Useful questions include:
   - What assumption is wrong?
   - What existing owner, code, concept, or analogous solved path was missed?
   - What state or failure case has not been considered?
   - Is the proposed mechanism larger than necessary?
   - Can something be removed rather than added?

4. Before adopting either agent's remedy, ChatGPT **generates its own materially different alternatives**, using both simplicity questions above, and independently challenges:
   - Is the defect itself established?
   - Are diagnosis and remedy being incorrectly treated as one conclusion?
   - Does the proposed change correct the fundamental cause rather than recover
     after it?
   - Has the first apparent solution been challenged against materially different
     alternatives: deletion, consolidation, narrower support, reuse, or deliberate
     non-automation?
   - What existing code, concept, owner, proof pattern, or solved case can be
     reused?
   - Can a user agreement, human prerequisite, clear refusal, bounded
     unsupported case, or deliberate non-automation eliminate machinery?
   - What new permanent responsibility does the solution create?
   - Would an ordinary later change to a requirement, interface, or shared
     feature force substantial rework elsewhere because of a hidden dependency?
     Can independent responsibilities, such as presentation and operational
     identity, remain separate without extra machinery?
   - Is the proof proportional to the actual changed invariant?
   - Is another agent's independent challenge likely to save more
     implementation/rework than it costs?

5. Once the mechanism and boundaries are settled, return the work to the agent
   currently best suited to implementation; current evidence often favors Claude
   for coordinated implementation across established owners.

6. Treat the sequence itself as provisional. Do not convert today's
   Claude/Codex/ChatGPT arrangement into permanent Studio architecture.
   Reevaluate as capabilities evolve.

## Current Provisional Decision Tree

- Need substantial first-pass repository understanding or integrated
  implementation?
  → Currently consider Claude first.

- Does the work involve a proposed new helper, owner, state mechanism, recovery
  path, architecture choice, provider/application behavior, or uncertainty
  about existing reuse?
  → Consider an independent Codex challenge before implementation.

- Has either agent proposed retries, recovery, fallback, patching, generalized
  defensive machinery, substantial new proof, or a new durable owner?
  → ChatGPT independently challenges root cause, reuse, human
  prerequisites/refusals, and whether the machinery should exist.

- Did Codex or Claude find a smaller existing mechanism or better-supported
  direction?
  → Prefer the smallest worthwhile result, then use the implementation agent
  best suited to carry it through the established owners.

- Is evidence weak, conflicting, or changing because agent/tool capability has
  changed?
  → Keep the conclusion provisional and gather more evidence rather than
  promoting it into a rule.

- Has repeated evidence made a practice useful enough to follow for now?
  → It may become an Active Evolving Practice or a dated Current Standing Rule,
  while remaining explicitly revisable.

This is a *current decision aid*, not automated routing or mandatory workflow machinery. In particular, consequential-work procedures and review ordering are mandatory independent of the provisional agent names in the table; a simplification review or refactoring task may warrant a different order from a runtime defect. Update the guide when evidence warrants it, rather than requiring the user to remember individual case histories.
